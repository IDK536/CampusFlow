# CampusFlow

ASP.NET Core API на .NET 10 и PostgreSQL 18. Совместный запуск предназначен для HTTP: браузер обращается к фронту, nginx передаёт `/api` сервису `backend`.

## Настройки

Нужны Docker с работающим Linux engine и Docker Compose. Для запуска API вне контейнера и тестов нужен .NET SDK 10.

Если `.env` ещё нет, скопируйте `.env.example` в `.env`. Если файл уже настроен, добавьте недостающие переменные, сохранив существующие подключения. Замените примеры `POSTGRES_PASSWORD` и `Jwt__Key` собственными значениями; ключ JWT должен содержать не менее 32 байт UTF-8. Для пароля контейнерной БД удобно использовать случайную строку из букв и цифр. `.env` исключён из Git и не попадает в образ API.

Основные настройки:

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | БД внутри Docker; создаются при первом запуске на пустом volume |
| `Jwt__Key`, `Jwt__Issuer`, `Jwt__Audience` | Подпись и проверка access JWT |
| `Auth__CookieSecure` | `false` для согласованного HTTP-режима вне Docker; без настройки API использует `true` |
| `Auth__AllowedOrigins__0`, `__1`, `__2` | Точные адреса фронта со схемой и портом: по умолчанию localhost:3000, :5173 и :4173 |
| `BACKEND_PORT`, `CLIENT_PORT` | Порты на localhost, по умолчанию 8080 и 3000 |
| `CLIENT_BUILD_CONTEXT` | Каталог с Dockerfile фронта; по умолчанию `./client` |
| `ConnectionStrings__CampusFlow` | Подключение при запуске API вне Docker |
| `CAMPUSFLOW_TEST_CONNECTION` | Подключение тестов к отдельной существующей БД `campusflow_test` |

Compose передаёт API собственную строку подключения к `db:5432`, не использует локальное подключение `ConnectionStrings__CampusFlow` и не передаёт тестовое подключение в контейнер. Порт PostgreSQL на хост не публикуется. В контейнер API передаётся `Auth__CookieSecure=false`, при этом `HttpOnly`, `SameSite=Lax` и путь `/api/auth` сохраняются.

Если меняете порт фронта или его hostname, измените и разрешённый Origin. Проверка Origin уже поддерживает явный список; proxy не обязан подменять браузерный Origin. Изменение пароля в `.env` не меняет пароль уже созданного пользователя в существующем volume PostgreSQL.

## Каталог фронта

Фронт разрабатывается отдельно, в ветке `frontend`. Если в текущем checkout уже есть `client`, оставьте `CLIENT_BUILD_CONTEXT='./client'`. Если каталога ещё нет, можно создать отдельный checkout без слияния веток:

```powershell
git fetch origin
git worktree add --detach ../CampusFlow-frontend origin/frontend
```

Затем задайте в `.env`:

```dotenv
CLIENT_BUILD_CONTEXT='../CampusFlow-frontend/client'
```

Compose использует существующий Dockerfile фронта, собирает его с `VITE_USE_MOCK=false` и передаёт nginx `API_UPSTREAM=http://backend:8080`. Браузер использует относительный `/api`; адрес `backend` существует только внутри Docker.

Реализация refresh, точные маршруты и типы ответов должны быть согласованы фронтом с реальным API. Сборка контейнеров сама по себе не подтверждает готовность всех сценариев интерфейса. Mock-режим и код клиента в этой ветке не изменяются.

## Первый запуск

Команды выполняются из корня репозитория. Сначала проверьте конфигурацию и явно инициализируйте БД:

```powershell
docker compose config --quiet
docker compose --profile tools run --build --rm init
```

`init` ждёт успешного healthcheck PostgreSQL, применяет миграции и запускает существующий seed. При ошибке инициализации остановитесь и проверьте её вывод. После успешного завершения:

```powershell
docker compose up --build -d backend client
docker compose ps
```

Адреса при настройках по умолчанию:

- Фронт: `http://localhost:3000`.
- API: `http://localhost:8080/api`.
- Swagger: `http://localhost:8080/swagger`; схема — `/swagger/v1/swagger.json`.

`init` использует тот же образ и настройки БД, что и API. Основной процесс API не применяет миграции и не запускает seed автоматически. Перед применением новых миграций сначала остановите обслуживающий запросы API и явно выполните инициализацию; она также запускает seed.

## Повторный запуск и данные

```powershell
docker compose stop
docker compose up -d backend client
```

Обычный повторный запуск не вызывает `init`. Данные сохраняются в именованном volume `postgres_data`, смонтированном в `/var/lib/postgresql` для PostgreSQL 18. Команда `docker compose down` удаляет контейнеры, но сохраняет этот volume.

Seed дополняет пользователей по login, аудитории по имени, брони по пользователю, аудитории, дате и интервалу. Уже существующие записи не перезаписываются. При повторном явном запуске в другой день относительные даты могут привести к добавлению новых демонстрационных броней; такой запуск не выполняется автоматически при рестарте.

Seed-аккаунты: `student1` / `student1`, `student2` / `student2`, `admin` / `admin`. Пароли хранятся как хеши. Создаются 12 аудиторий и 7 демонстрационных броней с датами относительно дня запуска seed. ID генерируются БД, фиксированные числовые значения для аккаунтов и аудиторий не предполагаются.

## API локально без Docker

Укажите рабочее подключение PostgreSQL в `ConnectionStrings__CampusFlow`, настройки JWT и `Auth__CookieSecure=false` для HTTP. При необходимости явно примените миграции и seed:

```powershell
dotnet run --project Backend/CampusFlow.Api.csproj -- --seed
```

Обычный запуск, совместимый с Vite proxy по умолчанию:

```powershell
dotnet run --project Backend/CampusFlow.Api.csproj --no-launch-profile --urls http://localhost:8080
```

Фронт может использовать `http://localhost:5173` и проксировать `/api` в этот API. Его настройки и код авторизации поддерживает фронтенд-разработчик.

## Тесты

Тесты используют существующую отдельную БД с именем `campusflow_test` из `CAMPUSFLOW_TEST_CONNECTION`. Перед прогоном проверьте эту настройку; рабочая или контейнерная БД приложения вместо неё не используется.

```powershell
dotnet test CampusFlow.slnx --verbosity minimal
```

Тесты применяют миграции, создают данные с GUID и удаляют собственные записи после выполнения. БД не создаётся и не удаляется, глобальной очистки таблиц нет. Единственный тест seed очищает свой набор. После успешного прогона на изначально пустой тестовой БД бизнес-таблицы остаются пустыми.

## Контракт и ограничения MVP

Авторизация: login, refresh и logout в `/api/auth`; access передаётся как Bearer, refresh — только в HttpOnly-cookie. Access по умолчанию действует 60 минут, refresh — 7 дней от входа, без продления. Обновления в одной вкладке необходимо объединять; межвкладочная координация в текущий MVP не входит.

Поиск: `GET /api/rooms`, параметры `building`, `minCapacity`, `equipment`, `date`, `startTime`, `endTime`. Без даты ответ — массив Room, с датой — `{date, rooms}` с `freeSlots`. Диапазон дат в административном списке не поддерживается: только `date`, `roomId`, `userId`, `status`.

Создание брони разрешено только student, владелец определяется по JWT. Интервалы внутри 09:00–18:00, шаг 30 минут, даты `YYYY-MM-DD`, время `HH:mm`, прошедшее начало запрещено. Смежные интервалы допустимы. Пересечение активных броней даёт `409 BOOKING_CONFLICT`, отмена сохраняет историю и освобождает время.

Административные операции требуют валидный JWT admin и текущую роль admin в БД. До подтверждения доступа возвращается одинаковый пустой `404`; после подтверждения — обычные ошибки ресурса и валидации. Удаление аудитории с любой историей запрещено: `409 ROOM_HAS_BOOKINGS`. Удаление без броней возвращает `204` без тела.

Пользователь содержит `displayName`, не `name`. Ошибка имеет `{code, message, details}`; ошибки полей содержат массивы сообщений. Неизвестные поля запроса игнорируются. Аналитика и прочие бонусы не обязательны для MVP.
