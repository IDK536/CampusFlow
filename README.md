# CampusFlow

Веб-сервис бронирования университетских аудиторий для хакатона IBS. Студент находит свободную аудиторию, проверяет время и бронирует её; администратор управляет справочником, просматривает и отменяет брони.

## Возможности

- Список аудиторий, фильтры по корпусу, вместимости и оборудованию, свободные интервалы на дату.
- Поиск свободного интервала одним запросом; API дополнительно поддерживает этаж, минимальную длительность и поиск по полному названию.
- Создание и отмена брони, личный список, разделение предстоящих и прошедших броней.
- Защита от пересечений в PostgreSQL: конфликт возвращает `409`, смежные интервалы разрешены.
- Административные CRUD аудиторий, просмотр и отмена любых броней.
- JWT, refresh в HttpOnly-cookie, восстановление входа после перезагрузки страницы.
- Рекомендации трёх аудиторий и CSV-экспорт на фронте; аналитика есть в интерфейсе и отдельном API.
- Расширения API: серверное время, пагинация, счётчики, история создания и отмены.

Дополнительные серверные возможности не все подключены к текущему интерфейсу: часть фильтрации, рекомендаций и аналитики фронт пока рассчитывает сам. Доступность новых API проверяется через Swagger или HTTP-запросы.

## Быстрый запуск с нуля через Docker

Нужны Git, запущенный Docker Engine/Desktop с Linux-контейнерами и Docker Compose. .NET и Node.js на хосте для этого варианта не требуются. Все команды ниже выполняются из корня репозитория.

```sh
git clone https://github.com/IDK536/CampusFlow.git
cd CampusFlow
```

Если репозиторий закрытый, предварительно настройте доступ к нему в Git. Для сдачи используйте согласованную ветку/коммит со всеми компонентами; рабочая интеграционная ветка — `develop`.

### 1. Настроить окружение

Создайте `Backend/.env` из [Backend/.env.example](Backend/.env.example), только если своего файла ещё нет.

Linux/macOS/Git Bash:

```sh
test -f Backend/.env || cp Backend/.env.example Backend/.env
```

PowerShell:

```powershell
if (!(Test-Path Backend/.env)) { Copy-Item Backend/.env.example Backend/.env }
```

В `Backend/.env` задайте случайный `Jwt__Key` минимум из 32 байт UTF-8. Не используйте строку-заглушку из шаблона. Например, в PowerShell 7 ключ можно сгенерировать так:

```powershell
[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
```

Обязательные для согласованного HTTP-демо настройки:

```dotenv
Jwt__Key=<случайный секрет минимум 32 байта>
Jwt__Issuer=CampusFlow
Jwt__Audience=CampusFlowClient
Jwt__AccessTokenMinutes=60
Jwt__RefreshTokenDays=7
Auth__CookieSecure=false
TZ=Europe/Moscow
```

Секреты не коммитятся и не попадают в сборку фронта. `Backend/.env` передаётся API и `init` через `env_file`, в Docker-образ не копируется. Не меняйте JWT-ключ между обычными перезапусками.

Текущий `compose.yaml` сам задаёт строку подключения к контейнеру `db` и локальные реквизиты PostgreSQL. Для Docker значение `ConnectionStrings__CampusFlow` из `.env` перекрывается Compose. Для запуска без Docker настройте эту строку отдельно.

Рабочие часы привязаны к локальной зоне API. `TZ=Europe/Moscow` задаётся и для инициализации, и для обычного API через один `.env`; после изменения окружения контейнеры нужно пересоздать. Для этой зоны `X-Server-Utc-Offset` должен быть `180`. Если TZ не задана, Linux-контейнер может работать по UTC, что изменит понятие «сегодня» и допустимое время бронирования.

### 2. Создать схему и демонстрационные данные

```sh
docker compose run --build --rm init
```

Команда поднимает PostgreSQL, ждёт его healthcheck, собирает API, применяет миграции, дополняет seed и завершается. HTTP-сервер в режиме `init` не запускается. Продолжайте после успешного завершения команды.

### 3. Запустить приложение

```sh
docker compose up --build -d
```

Открыть **http://localhost:3008**. Compose собирает фронт с `VITE_USE_MOCK=false`: запросы идут в настоящий API и PostgreSQL.

Проверка состояния и логов:

```sh
docker compose ps
docker compose logs --tail=100 backend client
```

Первое скачивание образов и зависимостей требует доступа к сети и занимает дольше повторного старта. Порт `3008` должен быть свободен.

## Остановка, повторный запуск и обновление

```sh
docker compose down
docker compose up -d
```

`down` сохраняет данные в именованном томе PostgreSQL. Не используйте `down --volumes` для обычной остановки: это удалит данные.

После изменения кода пересоберите приложение через `docker compose up --build -d`. Обычный API не применяет миграции и не запускает seed автоматически.

Если изменилась схема, примените миграции до запуска новой версии API. В текущем Compose для демо можно повторить `docker compose run --build --rm init`, но это запускает и seed. Для обновления только схемы используйте отдельный SDK/migration job или EF migration bundle. В SDK-окружении с настроенным подключением и `dotnet-ef` версии `10.0.12`, из папки `Backend`:

```sh
dotnet ef database update --project CampusFlow.Api.csproj --configuration Release
```

В runtime-контейнере ASP.NET нет SDK/EF CLI и нет флага приложения `--migrate`. Имя `db` доступно внутри сети Compose; с хоста нужна отдельно доступная БД и другая строка подключения.

## Seed и тестовые аккаунты

| Логин | Пароль | Роль |
|---|---|---|
| `student1` | `student1` | Студент |
| `student2` | `student2` | Студент |
| `admin` | `admin` | Администратор |

Первое заполнение создаёт 12 аудиторий в корпусах A–D, 3 пользователей и 6 студенческих броней на относительные даты. Пароли хранятся как хеши. ID создаёт БД: выбирайте аудиторию по названию, не рассчитывайте на фиксированные ID.

Seed добавляет недостающих пользователей по login, аудитории по названию, брони — по владельцу, аудитории, дате и интервалу. Существующие записи не перезаписывает и не удаляет. Повтор в тот же день не создаёт такие же записи; повтор в другой день может добавить брони на новые даты. Администратору демонстрационная бронь не создаётся.

Кнопка сброса mock-данных во фронте не очищает PostgreSQL. Перед демо при необходимости явно обновите seed и проверьте даты.

## Адреса, Swagger и HTTP

| Назначение | Адрес / поведение |
|---|---|
| Интерфейс в Compose | `http://localhost:3008` |
| API через nginx | `http://localhost:3008/api/...` |
| API внутри Docker | `http://backend:8080/api/...` |
| Swagger самого API | `/swagger` |
| OpenAPI самого API | `/swagger/v1/swagger.json` |

Текущий nginx проксирует только `/api/`. Поэтому `http://localhost:3008/swagger` не открывает Swagger API, а порт backend наружу по умолчанию не опубликован.

Чтобы открыть Swagger при уже работающем Compose, можно запустить дополнительный экземпляр того же API с явной публикацией порта (в отдельном терминале):

```sh
docker compose run --rm --no-deps -p 8080:8080 backend
```

Swagger: **http://localhost:8080/swagger**, OpenAPI: **http://localhost:8080/swagger/v1/swagger.json**. Порт `8080` должен быть свободен; `Ctrl+C` останавливает дополнительный экземпляр. Основной Compose продолжает работать. Для запросов нажмите Authorize и вставьте access-токен, полученный через `/api/auth/login`.

В HTTP-режиме требуется `Auth__CookieSecure=false`. Refresh-cookie имеет HttpOnly, SameSite=Lax и Path=/api/auth. Браузер работает через относительный `/api`; Docker-имена сервисов браузеру не доступны.

При доступе с другого компьютера используйте адрес сервера с портом `3008` и добавьте точный публичный origin в `Auth__AllowedOrigins__N` с незанятым индексом, например `__7`. Индексы 3–6 уже заданы в Compose и перекрывают одноимённые значения `.env`. Compose уже содержит несколько адресов демо; для новой машины их нужно актуализировать. При смене порта поправьте и разрешённые origins. Заголовок Host и cookie должны сохраняться при проксировании.

## Основной API

Base URL `/api`. JSON UTF-8; дата `YYYY-MM-DD`, время `HH:MM`. Защищённые запросы используют `Authorization: Bearer <access-token>`.

| Метод | Путь после `/api` | Назначение |
|---|---|---|
| POST | `/auth/login` | Вход; access в JSON, refresh в HttpOnly-cookie |
| POST | `/auth/refresh` | Ротация refresh, новый access |
| POST | `/auth/logout` | Выход, отзыв refresh-сессии |
| GET | `/rooms` | Список и объединённый поиск |
| GET | `/rooms/{id}` | Карточка аудитории |
| GET | `/rooms/{id}/free-slots?date=...` | Свободные интервалы |
| POST | `/bookings` | Создать бронь, только student |
| GET | `/bookings/my` | Собственные брони, только student |
| DELETE | `/bookings/{id}` | Отменить свою бронь |
| GET | `/admin/users` | Все студенты для административного фильтра |
| GET | `/admin/bookings` | Все брони, фильтры, сортировка и пагинация |
| DELETE | `/admin/bookings/{id}` | Отменить любую бронь |
| POST | `/admin/rooms` | Создать аудиторию |
| PUT | `/admin/rooms/{id}` | Полностью обновить аудиторию |
| DELETE | `/admin/rooms/{id}` | Удалить аудиторию без истории броней |
| GET | `/admin/stats` | Статистика за период |

Фильтры аудиторий: `building`, `floor`, `minCapacity`, `equipment` через запятую, `q`, `date`, `startTime`, `endTime`, `minDuration`. Оборудование применяется через AND. `q` ищет полное название без учёта регистра, не подстроку. С `minDuration` ищем одно непрерывное окно указанной длительности внутри заданного интервала; длительность >= 30 минут, кратна 30. Без него аудитория должна быть свободна весь заданный интервал.

Без даты `/rooms` возвращает массив; с датой — `{date, serverTime, utcOffset, rooms}`, у аудитории есть `freeSlots`. API показывает незанятые интервалы дня; прошедшее время блокирует фронт, а создание брони повторно проверяет сервер.

Для собственных броней: `status=active|cancelled`, `scope=upcoming|past`. Upcoming — активные, ещё не закончившиеся, включая текущую; past — закончившиеся независимо от статуса. Без scope доступны и будущие отменённые. Все условия объединяются через AND.

Административные брони поддерживают `date`, `dateFrom`, `dateTo`, `building`, `roomId`, `userId`, `status`, `q`, `sort=date|-date|room`, `limit=1..100`, `offset>=0`. `q` — полное имя пользователя ИЛИ полное название аудитории. Без limit возвращается весь список после offset. Заголовки `X-Total-Count` и `X-Active-Count` считают совпадения до пагинации; active определяется статусом, без самостоятельного ограничения датой.

У подтверждённого admin список и карточка аудитории дополнены `activeBookings` (active с датой >= сегодня, включая закончившиеся сегодня) и `hasBookings` (любая история). Для студентов поля отсутствуют. Любая история препятствует удалению аудитории: `409 ROOM_HAS_BOOKINGS`.

Статистика требует `dateFrom` и `dateTo`, опционально `building`. Только active, обе границы включены, ёмкость — число аудиторий × 540 минут × календарные дни. Ответ: totals, byBuilding, byDay, cells, byHalfHour, topRooms. Пустые даты/корпуса сохраняются, проценты дробные, рейтинг до 10 аудиторий.

В Booking есть `createdAt`, `cancelledAt`, `cancelledBy` (`owner`/`admin`/null). Старые неизвестные данные — null. Время создания выставляет PostgreSQL, первая отмена атомарно сохраняет время и автора; повторная отмена историю не меняет. Ответ отмены остаётся `{id, status}`.

Все ответы API содержат `X-Server-Time` и `X-Server-Utc-Offset`; ответы доступности также содержат эти значения в JSON. Время UTC, смещение — целые минуты. Общая форма ошибки: `{code, message, details}`, ошибки полей в details — массивы строк.

## Правила и ограничения MVP

- Рабочий день 09:00–18:00, сетка 30 минут. Прошедшие дата и время начала запрещены.
- Интервалы полуоткрытые: окончание в 15:00 и следующая бронь с 15:00 не конфликтуют.
- Студент видит только свои брони; чужая отмена возвращает `403`.
- Администратор не создаёт брони и работает с ними через административные маршруты.
- `/admin/*` до подтверждения JWT и актуальной роли admin возвращает пустой `404`, после подтверждения — обычные ошибки.
- Отмена сохраняет запись и освобождает интервал. Повторная отмена — `409 ALREADY_CANCELLED`.
- Access действует 60 минут, refresh — 7 дней от входа; ротация не продлевает первоначальный срок. Межвкладочная синхронизация refresh отложена.
- В реальном режиме две вкладки одного браузерного профиля используют общую cookie. Для параллельной демонстрации разных пользователей используйте разные профили/браузеры.
- Нет интеграции с расписанием вуза, 1С или Telegram. Нет push-обновления занятости: при гонке сервер возвращает `409`.
- Прошедшая бронь может иметь status=active; завершённость по времени не меняет статус автоматически.
- История использует текущие имена пользователей, названия и корпуса аудиторий, а не исторические снимки справочников.
- Docker-конфигурация рассчитана на демо: локальные реквизиты БД и разрешённые origins заданы в Compose. При размещении на другой машине конфигурацию нужно изменить.

## Сценарий демонстрации: около 5 минут

На свежем seed, при согласованной зоне времени API и браузера:

1. **Список и фильтры.** Войти как student1, выбрать завтра, корпус B, от 20 мест и projector: должны остаться B-101 и B-204.
2. **Свободные слоты.** Открыть B-101: seed занимает завтра 09:00–10:30, после 10:30 есть свободное время.
3. **Успешная бронь.** Забронировать завтра 14:00–15:00; получить подтверждение, проверить собственный список (`201` на API).
4. **Конфликт.** В другом браузерном профиле student2 заранее выбирает этот интервал до создания брони student1, затем отправляет заявку: `409 BOOKING_CONFLICT`. Либо повторить POST через Swagger с другим access-токеном.
5. **Своя отмена.** Student1 отменяет бронь: `200`, статус cancelled, слот снова свободен.
6. **Права.** Через Swagger/API student2 пытается отменить эту чужую бронь по её фактическому ID: `403 FORBIDDEN`, чужая запись не меняется.
7. **Администратор.** Admin открывает «Все брони», выбирает завтра или период на три дня (по умолчанию интерфейс показывает сегодня), отменяет бронь student2, создаёт/редактирует аудиторию; удаление аудитории с историей возвращает `409`. Показать аналитику, подбор трёх вариантов и CSV.
8. **Воспроизводимость запуска.** Показать команды первого запуска, seed-аккаунты, Swagger и сохранение данных после перезапуска. Полную сборку подготовить до начала пяти минут.

Сценарий предполагает исходные данные. При повторном показе выберите свободный слот или учтите уже созданные/отменённые записи; seed не сбрасывает изменения.

## Разработка без Docker

Backend: .NET SDK 10, PostgreSQL 18, существующая рабочая БД, заполненный `Backend/.env`. Из `Backend/`:

```sh
dotnet run --project CampusFlow.Api.csproj -- --seed
dotnet run --project CampusFlow.Api.csproj --no-launch-profile --urls http://localhost:8080
```

Для фронта нужен Node.js 24. Из `client/` выполните `npm ci`, создайте `.env.local` с `VITE_USE_MOCK=false` и `VITE_API_TARGET=http://localhost:8080`, затем `npm run dev`. Vite открывает интерфейс на `http://localhost:5173` и проксирует `/api`. Настройки Compose при таком запуске не применяются.

Если нужен отдельный mock-режим фронта, оставьте `VITE_USE_MOCK=true`: это данные браузера, они не проверяют интеграцию с настоящим API.

## Тесты и проверки

Backend: отдельная существующая БД строго с именем `campusflow_test`; строка задаётся в `CAMPUSFLOW_TEST_CONNECTION` в `Backend/.env` или окружении процесса. Тесты применяют миграции, создают уникальные данные и удаляют свои записи. Рабочая БД не используется; сама тестовая база не создаётся и не удаляется.

Из корня репозитория:

```sh
dotnet test Backend/CampusFlow.slnx --configuration Release
```

Для тестов на хосте используйте доступный с хоста PostgreSQL: сервис db текущего Compose не публикует 5432 наружу. При первом запуске приложения тестовая БД не нужна.

Frontend, из `client/`:

```sh
npm ci
npm run lint -- src vite.config.ts
npm test
npm run build
```

Тесты фронта проверяют в том числе mock-сценарии, подбор и CSV; они не заменяют проверку реального приложения. CI описан в [.github/workflows/ci.yml](.github/workflows/ci.yml): backend проверяется с PostgreSQL 18, frontend — на Node.js 24.

## Что проверено в Docker

- Создание 201, конфликт 409, запрет чужой отмены 403, отмена и освобождение времени, административный CRUD, статистика и refresh/logout с cookie.

- Frontend: production-сборка, lint без предупреждений и ошибок, 63 теста Vitest. Эти проверки не заменяют ручной прогон всех экранов браузера.

## Если запуск не удался

- Нет `Backend/.env`: создайте файл по шаблону до вызова Compose.
- API завершается из-за JWT: проверьте ключ минимум 32 байта, issuer и audience; смотрите `docker compose logs backend`.
- Ошибка отсутствующей таблицы/колонки: сначала выполните init или примените миграции, затем запустите API.
- Фронт работает, но API недоступен: проверьте backend/db и `API_UPSTREAM`; текущий внешний адрес API начинается с `/api` на порту 3008.
- Refresh не работает по HTTP: проверьте `Auth__CookieSecure=false`, разрешённый origin и сохранение cookie.
- Ошибка `403` при входе с нового адреса: добавьте этот origin в настройки API и пересоздайте backend.
- Данные выглядят независимыми от сервера: убедитесь, что фронт собран с `VITE_USE_MOCK=false`; одной переменной окружения запущенного nginx недостаточно.
- Слоты/даты сдвинуты: проверьте TZ API и браузера, заголовки времени и фактические даты seed.
- `/swagger` на порту 3008 показывает интерфейс: это ожидаемо для текущего nginx; используйте отдельную публикацию API на 8080, описанную выше.
