# Сверка эндпоинтов фронта с ТЗ и API

Проверены предоставленный FRONTEND_ENDPOINTS.md, DOCX, утверждённые решения по PDF/DOCX, контроллеры бэкенда и код ветки origin/frontend на коммите 48433d2. Это сверка контракта и исходников, а не результат полного браузерного прогона. Код фронта не менялся.

## Полный список выявленных разногласий

Пункты относятся к проверенной версии frontend 48433d2. Они не означают, что вся реализация фронта нарушает ТЗ. Исправления ниже выполняются на стороне фронта; новые маршруты и расширения бэкенда под прежние предположения не добавляются.

| № | Разногласие | Что требуется или реализовано на бэкенде | Что исправить на фронте |
| --- | --- | --- | --- |
| 1 | Корпуса A–T вместо A–D | DOCX и API разрешают только A/B/C/D | Ограничить тип Building, BUILDINGS, варианты выбора и mock-валидацию |
| 2 | Поиск и удаление обозначены как «вне ТЗ» | Они выходят за перечень методов DOCX, но предусмотрены PDF и уже утверждены командой | Уточнить документацию: это согласованные функции, а не новые необязательные запросы к бэкенду |
| 3 | Поиск вызывается по /api/rooms/search | Объединённый поиск находится в GET /api/rooms | Исправить SEARCH_PATH на /rooms с учётом baseURL=/api |
| 4 | Ожидается массив RoomWithSlots[] при поиске с датой | С date возвращается {date, rooms}, без date — массив Room | Добавить тип ответа с оболочкой и возвращать response.data.rooms для поиска с датой |
| 5 | Запасной поиск включается только после 404/405 | /api/rooms/search для авторизованного пользователя попадает в маршрут с числовым id и даёт 400; обход отдельными запросами также не выполняет требование поиска одним запросом | После исправления адреса удалить запасной обход; не расширять его на 400 |
| 6 | Отправляются dateFrom/dateTo как параметры API | Сервер поддерживает только date, roomId, userId, status; неизвестные параметры игнорирует | Для одного дня отправлять date, для периода оставить существующую клиентскую фильтрацию, не рассчитывать на серверную поддержку периода |
| 7 | Ошибки полей ожидаются как строки, массивы отбрасываются | details для 400 содержит массивы сообщений по полям; это выбранный API-контракт, точный формат значений DOCX не определяет | Поддержать string[] в adminSaga и выводе формы; для неизвестных полей/JSON-путей предусмотреть общий вывод |
| 8 | Mock запрещает удаление только при активных непрошедших бронях | Любая связанная бронь, включая отменённую или прошлую, даёт 409 ROOM_HAS_BOOKINGS | Исправить mock-проверку и сообщение; не обещать, что отмена всех броней разрешит удалить аудиторию |
| 9 | Пустой административный 404 показывается как обычное «Не найдено» | До подтверждения admin возвращается пустой 404 без причины; согласовано нейтральное сообщение | Для пустого admin-404 показывать «Операция недоступна» и не запускать refresh по одному этому статусу |
| 10 | Refresh и backend-logout не подключены | POST /api/auth/refresh и POST /api/auth/logout уже существуют | Добавить вызовы этих методов и восстановление входа через refresh-cookie; refresh/logout не должны требовать действительный access |
| 11 | Access и user сохраняются в sessionStorage, при истечении access вход завершается | Согласованы access в памяти, HttpOnly refresh-cookie и восстановление сессии через refresh | Заменить хранение и завершение сессии по одному лишь exp; не хранить refresh в JavaScript-хранилищах |
| 12 | Нет согласованного единого refresh внутри вкладки и предварительного обновления access | Повтор использованного refresh отзывает сессию; административный отказ не даёт 401 | Объединять обновления одним Promise, проверять срок access перед запросом, после успешного refresh выполнять не более одного повтора; 401 самого refresh завершает вход |
| 13 | Booking.comment объявлен только string | В ответе допускается null, в запросе comment необязателен | Уточнить типы ответа и запроса; в просмотренных компонентах вывод уже защищён проверкой значения, падение интерфейса не доказано |
| 14 | Наличие HTTP-функций можно принять за готовую интеграцию, хотя по умолчанию выбран mockGateway | Реальные маршруты обслуживает API; mock не проверяет совместимость с ним | Для интеграционной проверки явно задать VITE_USE_MOCK=false и повторить сценарии с настоящим сервером |

Пункт 1 — прямое несовпадение с ограничением DOCX. Пункт 2 уточняет трактовку PDF/DOCX. Остальные пункты относятся к согласованному контракту, интеграции или типам; их нельзя автоматически называть прямым нарушением исходного ТЗ.

## Что не является найденным разногласием

- User.displayName уже правильно указан в коде фронта. Замена на name не требуется.
- Параметры startTime/endTime для BOOKING_CONFLICT приходят в details, как ожидает фронт и показывает DOCX.
- Метод удаления аудитории, ответ 204 и код ROOM_HAS_BOOKINGS выбраны правильно; расходится именно mock-условие запрета удаления.
- Клиентская аналитика и фильтрация периода не требуют нового API и сами по себе не нарушают обязательный MVP.
- Межвкладочная синхронизация, Web Locks/BroadcastChannel и grace-окно refresh отложены по указанию владельца проекта. Их отсутствие не входит в список обязательных исправлений текущего MVP.
- Docker передан другому разработчику и не входит в эту работу.

## Что реализовано

В работающем Swagger бэкенда подтверждены 14 операций. В файле фронта перечислено 13 вызовов: 12 маршрутов существуют, один маршрут поиска неверный. Два существующих auth-метода фронт ещё не подключил. Совпадение маршрута не означает совпадение всех типов и поведения.

Все пути ниже включают общий префикс /api.

| Метод и путь | Состояние |
| --- | --- |
| POST /api/auth/login | Реализован с обеих сторон; ответ {token, user}, user содержит displayName |
| POST /api/auth/refresh | Реализован на бэкенде, не подключён во фронте; использует HttpOnly-cookie, возвращает {token, user} |
| POST /api/auth/logout | Реализован на бэкенде, не подключён во фронте; отзывает refresh-сессию и удаляет cookie, ответ 204 |
| GET /api/rooms | Реализован; без date массив Room, с date объект {date, rooms} с freeSlots |
| GET /api/rooms/{id} | Маршрут и контракт совпадают |
| GET /api/rooms/{id}/free-slots?date=YYYY-MM-DD | Маршрут и контракт совпадают |
| GET /api/rooms/search | Такого отдельного метода нет; используется GET /api/rooms с параметрами даты и времени |
| POST /api/bookings | Реализован; при 409 BOOKING_CONFLICT details содержит roomId, date, startTime, endTime |
| GET /api/bookings/my | Реализован, необязательный status=active/cancelled |
| DELETE /api/bookings/{id} | Реализован; ответ 200 {id, status: cancelled} |
| GET /api/admin/bookings | Реализован; фильтры только date, roomId, userId, status |
| DELETE /api/admin/bookings/{id} | Реализован; ответ 200 {id, status: cancelled} |
| POST /api/admin/rooms | Реализован, 201 Room; обработку ошибок полей во фронте нужно исправить |
| PUT /api/admin/rooms/{id} | Реализован, 200 Room; все пять полей обязательны |
| DELETE /api/admin/rooms/{id} | Реализован, 204 без тела; любая связанная бронь запрещает удаление с 409 ROOM_HAS_BOOKINGS |

HTTP-обработчики написаны в client/src/api/httpGateway.ts. Но client/src/api/gateway.ts по умолчанию выбирает mockGateway, пока VITE_USE_MOCK не задан строго как false. Поэтому наличие функций ещё не подтверждает работу интерфейса с настоящим API.

## Что расходится с ТЗ

1. **Корпуса A–T вместо A–D.** В client/src/api/types.ts и client/src/data/equipment.ts разрешены A–T; этот список используется выбором корпуса и mock-валидацией. DOCX разрешает только A/B/C/D. Наш API отклоняет E–T с 400. Фронту нужно ограничить типы, варианты выбора и mock-валидацию.
2. **Нельзя считать поиск одним запросом и удаление аудитории просто «вне ТЗ».** В DOCX отдельный поиск необязателен, DELETE Room не описан; PDF требует поиск одним запросом и полный CRUD. Мы уже согласовали эти возможности. Произвольное имя /rooms/search не является само по себе нарушением ТЗ, но не совпадает с выбранным API. Запасной поиск отдельными запросами покрывает DOCX, но не требование PDF о едином запросе.
3. **Остальные замечания ниже — преимущественно несовпадения с нашей реализацией и договорённостями.** ТЗ не задаёт точный формат ошибок полей внутри details для 400 и не описывает нашу refresh-схему. Поэтому некорректно называть отсутствие refresh или ожидание строк в details прямым нарушением исходного DOCX.

## Что не совпадает с нашей реализацией

### Поиск: маршрут, ответ и запасной путь

Фронт вызывает /api/rooms/search и ожидает RoomWithSlots[]. Нужно вызывать:

```text
GET /api/rooms?building=A&minCapacity=20&equipment=projector,whiteboard&date=2026-11-16&startTime=14:00&endTime=15:00
```

С date ответ — {date, rooms}, массив берётся из rooms. Параметры характеристик необязательны, время передаётся парой и требует дату. При отсутствии результатов rooms пуст.

Сейчас /api/rooms/search попадает в общий маршрут /api/rooms/{id}; для подтверждённого student/admin значение search не преобразуется в int, получается 400 VALIDATION_ERROR. Следовательно, запасной путь фронта, запускаемый только на 404/405, этот случай не исправляет. Нужно исправить маршрут и убрать запасной обход, а не расширять список ошибок для его запуска.

### Период административного списка

dateFrom/dateTo не поддерживаются сервером и игнорируются как неизвестные параметры. Сервер возвращает все записи, подходящие под остальные фильтры; фронт действительно дополнительно фильтрует массив по периоду в httpGateway.ts. Это может работать для MVP, но не является серверной фильтрацией периода. Новые параметры API сейчас не добавляем. Один день передаётся как date.

### Ошибки полей

Бэкенд возвращает details в виде {field: string[]}, например:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Некорректные данные запроса",
  "details": {
    "name": ["Аудитория с таким названием уже существует"]
  }
}
```

client/src/redux/saga/adminSaga.ts сейчас оставляет только значения typeof v === string, поэтому массивы от API отбрасываются и ошибки у полей пропадают. Нужно преобразовать массив в сообщение или поддержать несколько сообщений. Для ошибок JSON ключ может быть путём вроде $.floor; неизвестные полю ошибки нужно показывать общим сообщением.

### Удаление аудитории и mock-данные

Документ фронта описывает 204 и 409 правильно. Но mockGateway.ts запрещает удалять только при активных бронях с датой не раньше сегодняшней. Наш API запрещает удаление при любой брони: активной/отменённой, прошлой/будущей. Отмена броней сама по себе не разрешает удаление аудитории с историей. Mock-поведение и его сообщение нужно привести к утверждённому правилу.

### Административный 404

Наши административные методы проверяют JWT и текущую роль в БД до валидации. Неподтверждённый доступ получает одинаковый пустой 404. Это утверждённое отличие от DOCX с 403. Фронт уже умеет преобразовать пустой ответ в общую ошибку, но сейчас показывает «Не найдено». Для этого случая согласовано нейтральное «Операция недоступна», без запуска refresh по любому 404.

### Авторизация и типы данных

- Refresh/logout отсутствуют в Gateway и HTTP-шлюзе. Access и user пока сохраняются в sessionStorage; согласованный переход — access в памяти, восстановление входа через refresh-cookie, один refresh внутри вкладки. Межвкладочную координацию в MVP не добавляем.
- User.displayName в актуальном types.ts уже соответствует ТЗ и бэкенду. Прежний вопрос из ответов фронта про user.name не подтверждается его текущим кодом и не считается найденной ошибкой.
- Booking.comment на бэкенде допускает null, создание разрешает отсутствие comment; фронтовые типы пока требуют string. Показанные компоненты защищают вывод проверкой значения, поэтому это замечание к типам, а не доказанное падение интерфейса.
- Формат details для BOOKING_CONFLICT совпадает с ожиданием фронта и примером DOCX; startTime/endTime приходят.

## Swagger

При запуске API на HTTP 8080 проверены ответы 200:

- UI: http://localhost:8080/swagger/index.html (также /swagger).
- OpenAPI JSON: http://localhost:8080/swagger/v1/swagger.json.
- Base URL API: http://localhost:8080/api.

Команда из Backend:

```powershell
dotnet run --project CampusFlow.Api.csproj --no-launch-profile --urls http://localhost:8080
```

Swagger доступен без авторизации. Для защищённых методов используется Authorize с access JWT. URL работают, пока запущен процесс API. Код фронта, новый поиск по периоду, grace-окно и Docker в рамках этой сверки не изменялись.
