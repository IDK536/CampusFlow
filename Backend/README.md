# CampusFlow Backend

[Сверка эндпоинтов фронта с ТЗ и API](FRONTEND_ENDPOINTS_REVIEW.md).

ASP.NET Core API на .NET 10 и PostgreSQL 18. Исходники API, тесты, решение, шаблон окружения и эта инструкция находятся в Backend. Команды ниже выполняются из этой папки.

## Настройки

Нужны .NET SDK 10 и работающий PostgreSQL 18. Создайте рабочую базу приложения; для интеграционных тестов отдельно нужна существующая база с именем campusflow_test.

Если локального .env ещё нет, скопируйте .env.example в .env. Если он уже настроен, сохраните существующие значения. Укажите ConnectionStrings__CampusFlow, CAMPUSFLOW_TEST_CONNECTION и настройки JWT. Jwt__Key должен содержать не менее 32 байт UTF-8; пример в шаблоне замените случайным ключом. Локальный .env исключён из Git.

HTTP-настройки:

- Auth__CookieSecure=false для согласованного HTTP-режима. Без этой настройки API использует true.
- Auth__AllowedOrigins__0=http://localhost:3000.
- Auth__AllowedOrigins__1=http://localhost:5173.
- Auth__AllowedOrigins__2=http://localhost:4173.

Разрешённые Origin должны точно совпадать с адресами фронта, включая схему и порт. Refresh-cookie сохраняет HttpOnly, SameSite=Lax и Path=/api/auth. Значения окружения процесса имеют приоритет над .env.

## Миграции и seed

Явная инициализация рабочей БД:

```powershell
dotnet run --project CampusFlow.Api.csproj -- --seed
```

Команда применяет миграции и дополняет seed. Обычный запуск API не делает этого автоматически. Пользователи проверяются по login, аудитории по названию, брони по пользователю, аудитории, дате и интервалу. Существующие записи не перезаписываются.

Повторный явный запуск в другой день может добавить демонстрационные брони с новыми относительными датами. Если требуется только перезапустить API, --seed не передавайте.

Seed-аккаунты: student1 / student1, student2 / student2, admin / admin. Пароли хранятся как хеши. Создаются 12 аудиторий и 6 демонстрационных броней студентов. Администратору seed брони не создаёт; ранее существовавшие записи не удаляет. ID генерируются БД, фиксированные значения не предполагаются.

## Запуск по HTTP

```powershell
dotnet run --project CampusFlow.Api.csproj --no-launch-profile --urls http://localhost:8080
```

API доступен по http://localhost:8080/api, Swagger — http://localhost:8080/swagger, схема — /swagger/v1/swagger.json. Фронт использует относительный /api через свой proxy; для Vite целевой адрес API — http://localhost:8080. Код фронта поддерживает фронтенд-разработчик.

Остановка и повторный обычный запуск не удаляют данные PostgreSQL и не вызывают seed.

## Тесты и сборка

```powershell
dotnet test CampusFlow.slnx --verbosity minimal
dotnet publish CampusFlow.Api.csproj -c Release
```

Решение включает CampusFlow.Api.csproj и Tests/CampusFlow.Api.Tests.csproj. Тестовые исходники исключены из автоматического включения в API-проект.

Тесты используют отдельную существующую БД campusflow_test из CAMPUSFLOW_TEST_CONNECTION. Применение миграций в подготовке тестов выполняется через общий TestDatabase последовательно; выполнение самих тестов не отключает стандартную параллельность xUnit. Они применяют миграции, создают данные с GUID и удаляют собственные записи после выполнения. БД не создаётся и не удаляется, глобальной очистки таблиц нет. Единственный тест seed очищает свой набор. После успешного прогона на изначально пустой БД бизнес-таблицы остаются пустыми.

## Контракт MVP

Login, refresh и logout находятся в /api/auth. Access JWT передаётся как Bearer, refresh — только в HttpOnly-cookie. По умолчанию access действует 60 минут, refresh — 7 дней от входа без продления. Обновления внутри одной вкладки объединяются; межвкладочная синхронизация и grace-окно в текущий MVP не входят.

Поиск: GET /api/rooms с building, minCapacity, equipment, floor, date, startTime, endTime, minDuration. Без даты возвращается массив Room, с датой — {date, serverTime, utcOffset, rooms} с freeSlots. Административный список поддерживает building, date, dateFrom, dateTo, roomId, userId, status. Границы периода включительные, каждая необязательна; прошлые даты разрешены. Формат YYYY-MM-DD, начало позже конца даёт 400. Все фильтры объединяются через AND; date сохраняет выбор одного дня.

Создание брони доступно только student, владелец определяется из JWT. Интервалы внутри 09:00–18:00 с шагом 30 минут, дата YYYY-MM-DD и время HH:mm, прошедшее начало запрещено. Смежные интервалы допустимы. Пересечение активных броней даёт 409 BOOKING_CONFLICT. Отмена сохраняет историю и освобождает интервал.

Административные операции требуют валидный JWT admin и текущую роль admin в БД. До подтверждения доступа возвращается одинаковый пустой 404. Удаление аудитории с любой историей даёт 409 ROOM_HAS_BOOKINGS; без броней — 204 без тела.

Пользователь содержит displayName, не name. Ошибка имеет {code, message, details}; ошибки полей содержат массивы сообщений. Неизвестные поля запроса игнорируются. Аналитика и другие бонусы не обязательны для MVP.

## Расширения поиска и время сервера

Каждый ответ /api содержит X-Server-Time (ISO 8601 UTC) и X-Server-Utc-Offset (целое число минут локального смещения сервера относительно UTC, например 180). Заголовки доступны браузеру через CORS для разрешённых Origin. Время фиксируется один раз при входе запроса в middleware через TimeProvider. В ответах GET /api/rooms с date и GET /api/rooms/{id}/free-slots те же значения есть в полях serverTime и utcOffset. Имя массива индивидуального ответа остаётся freeSlots.

Используется локальный часовой пояс сервера, как при проверке начала бронирования. Отдельной настройки часового пояса кампуса нет. Свободные интервалы не обрезаются по текущему времени: фронт по серверным часам блокирует прошедшие слоты; POST /api/bookings по-прежнему запрещает начало в прошлом. Заголовки описывают время при получении запроса, а не момент отправки ответа; при синхронизации фронт учитывает задержку сети.

floor — целый этаж не меньше 1, точное совпадение в БД; работает с датой и без неё, совместно с остальными фильтрами.

minDuration — целое число минут >= 30, кратное 30; требует date, startTime и endTime и не может превышать длину промежутка. Пример: GET /api/rooms?date=2035-01-01&startTime=12:00&endTime=16:00&minDuration=60. Отбираются аудитории хотя бы с одним непрерывным свободным окном нужной длительности внутри границ поиска. В freeSlots остаются только подходящие окна, ограниченные этими границами. Раздельные окна не складываются. Прошедшие часы сегодня автоматически не исключаются. Без minDuration сохраняется прежний поиск свободного целиком интервала и выдача свободных окон всего дня. Неверные параметры дают 400 VALIDATION_ERROR.

## Студенты и корпус в административных бронях

GET /api/admin/users возвращает массив {id, login, displayName, role} только для student, включая студентов без броней. Порядок: displayName, затем id. Пароли и хеши не выбираются из БД. Нет студентов — 200 []. Параметров фильтрации у этого метода нет. Доступ требует валидного JWT admin и актуальной роли admin в БД; до подтверждения доступа ответ — пустой 404 без WWW-Authenticate.

GET /api/admin/bookings?building=A ограничивает список текущим корпусом связанной аудитории. Допустимы только A, B, C, D; пустое или неверное значение даёт 400 VALIDATION_ERROR после проверки административного доступа. Условие применяется в БД через JOIN вместе с date/dateFrom/dateTo/roomId/userId/status через AND. Без building поведение не меняется. Перенос аудитории в другой корпус отражается в фильтре исторических броней: отдельный снимок корпуса при создании брони не хранится.
