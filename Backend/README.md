# CampusFlow Backend

[Сверка эндпоинтов фронта с ТЗ и API](FRONTEND_ENDPOINTS_REVIEW.md).

ASP.NET Core API на .NET 10 и PostgreSQL 18. Исходники API, тесты, решение, шаблон окружения и эта инструкция находятся в Backend. Команды ниже выполняются из этой папки.

## Настройки

Нужны .NET SDK 10 и работающий PostgreSQL 18. Создайте рабочую базу приложения; для интеграционных тестов отдельно нужна существующая база с именем campusflow_test.

Если локального .env ещё нет, скопируйте .env.example в .env. Если он уже настроен, сохраните существующие значения. Укажите ConnectionStrings__CampusFlow, CAMPUSFLOW_TEST_CONNECTION и настройки JWT. Jwt__Key должен содержать не менее 32 байт UTF-8; пример в шаблоне замените случайным ключом. Локальный .env исключён из Git.

HTTP-настройки:

- Auth__CookieSecure=false для согласованного HTTP-режима. Без этой настройки API использует true.
- Auth__AllowedOrigins__0=http://localhost:3000.
- Auth__AllowedOrigins__1=http://localhost:5173.
- Auth__AllowedOrigins__2=http://localhost:4173.

Разрешённые Origin должны точно совпадать с адресами фронта, включая схему и порт. Refresh-cookie сохраняет HttpOnly, SameSite=Lax и Path=/api/auth. Значения окружения процесса имеют приоритет над .env.

## Миграции и seed

Явная инициализация рабочей БД:

```powershell
dotnet run --project CampusFlow.Api.csproj -- --seed
```

Команда применяет миграции и дополняет seed. Обычный запуск API не делает этого автоматически. Пользователи проверяются по login, аудитории по названию, брони по пользователю, аудитории, дате и интервалу. Существующие записи не перезаписываются.

Повторный явный запуск в другой день может добавить демонстрационные брони с новыми относительными датами. Если требуется только перезапустить API, --seed не передавайте.

Seed-аккаунты: student1 / student1, student2 / student2, admin / admin. Пароли хранятся как хеши. Создаются 12 аудиторий и 6 демонстрационных броней студентов. Администратору seed брони не создаёт; ранее существовавшие записи не удаляет. ID генерируются БД, фиксированные значения не предполагаются.

## Запуск по HTTP

```powershell
dotnet run --project CampusFlow.Api.csproj --no-launch-profile --urls http://localhost:8080
```

API доступен по http://localhost:8080/api, Swagger — http://localhost:8080/swagger, схема — /swagger/v1/swagger.json. Фронт использует относительный /api через свой proxy; для Vite целевой адрес API — http://localhost:8080. Код фронта поддерживает фронтенд-разработчик.

Остановка и повторный обычный запуск не удаляют данные PostgreSQL и не вызывают seed.

## Тесты и сборка

```powershell
dotnet test CampusFlow.slnx --verbosity minimal
dotnet publish CampusFlow.Api.csproj -c Release
```

Решение включает CampusFlow.Api.csproj и Tests/CampusFlow.Api.Tests.csproj. Тестовые исходники исключены из автоматического включения в API-проект.

Тесты используют отдельную существующую БД campusflow_test из CAMPUSFLOW_TEST_CONNECTION. Применение миграций в подготовке тестов выполняется через общий TestDatabase последовательно; выполнение самих тестов не отключает стандартную параллельность xUnit. Они применяют миграции, создают данные с GUID и удаляют собственные записи после выполнения. БД не создаётся и не удаляется, глобальной очистки таблиц нет. Единственный тест seed очищает свой набор. После успешного прогона на изначально пустой БД бизнес-таблицы остаются пустыми.

## Контракт MVP

Login, refresh и logout находятся в /api/auth. Access JWT передаётся как Bearer, refresh — только в HttpOnly-cookie. По умолчанию access действует 60 минут, refresh — 7 дней от входа без продления. Обновления внутри одной вкладки объединяются; межвкладочная синхронизация и grace-окно в текущий MVP не входят.

Поиск: GET /api/rooms с q, building, minCapacity, equipment, floor, date, startTime, endTime, minDuration. Без даты возвращается массив Room, с датой — {date, serverTime, utcOffset, rooms} с freeSlots. Административный список поддерживает q, building, date, dateFrom, dateTo, roomId, userId, status, sort, limit, offset. Границы периода включительные, каждая необязательна; прошлые даты разрешены. Формат YYYY-MM-DD, начало позже конца даёт 400. Все фильтры объединяются через AND; date сохраняет выбор одного дня.

Создание брони доступно только student, владелец определяется из JWT. Интервалы внутри 09:00–18:00 с шагом 30 минут, дата YYYY-MM-DD и время HH:mm, прошедшее начало запрещено. Смежные интервалы допустимы. Пересечение активных броней даёт 409 BOOKING_CONFLICT. Отмена сохраняет историю и освобождает интервал.

Административные операции требуют валидный JWT admin и текущую роль admin в БД. До подтверждения доступа возвращается одинаковый пустой 404. Удаление аудитории с любой историей даёт 409 ROOM_HAS_BOOKINGS; без броней — 204 без тела.

Пользователь содержит displayName, не name. Ошибка имеет {code, message, details}; ошибки полей содержат массивы сообщений. Неизвестные поля запроса игнорируются. Аналитика и другие бонусы не обязательны для MVP.

## Расширения поиска и время сервера

Каждый ответ /api содержит X-Server-Time (ISO 8601 UTC) и X-Server-Utc-Offset (целое число минут локального смещения сервера относительно UTC, например 180). Заголовки доступны браузеру через CORS для разрешённых Origin. Время фиксируется один раз при входе запроса в middleware через TimeProvider. В ответах GET /api/rooms с date и GET /api/rooms/{id}/free-slots те же значения есть в полях serverTime и utcOffset. Имя массива индивидуального ответа остаётся freeSlots.

Используется локальный часовой пояс сервера, как при проверке начала бронирования. Отдельной настройки часового пояса кампуса нет. Свободные интервалы не обрезаются по текущему времени: фронт по серверным часам блокирует прошедшие слоты; POST /api/bookings по-прежнему запрещает начало в прошлом. Заголовки описывают время при получении запроса, а не момент отправки ответа; при синхронизации фронт учитывает задержку сети.

floor — целый этаж не меньше 1, точное совпадение в БД; работает с датой и без неё, совместно с остальными фильтрами.

minDuration — целое число минут >= 30, кратное 30; требует date, startTime и endTime и не может превышать длину промежутка. Пример: GET /api/rooms?date=2035-01-01&startTime=12:00&endTime=16:00&minDuration=60. Отбираются аудитории хотя бы с одним непрерывным свободным окном нужной длительности внутри границ поиска. В freeSlots остаются только подходящие окна, ограниченные этими границами. Раздельные окна не складываются. Прошедшие часы сегодня автоматически не исключаются. Без minDuration сохраняется прежний поиск свободного целиком интервала и выдача свободных окон всего дня. Неверные параметры дают 400 VALIDATION_ERROR.

## Студенты и корпус в административных бронях

GET /api/admin/users возвращает массив {id, login, displayName, role} только для student, включая студентов без броней. Порядок: displayName, затем id. Пароли и хеши не выбираются из БД. Нет студентов — 200 []. Параметров фильтрации у этого метода нет. Доступ требует валидного JWT admin и актуальной роли admin в БД; до подтверждения доступа ответ — пустой 404 без WWW-Authenticate.

GET /api/admin/bookings?building=A ограничивает список текущим корпусом связанной аудитории. Допустимы только A, B, C, D; пустое или неверное значение даёт 400 VALIDATION_ERROR после проверки административного доступа. Условие применяется в БД через JOIN вместе с date/dateFrom/dateTo/roomId/userId/status через AND. Без building поведение не меняется. Перенос аудитории в другой корпус отражается в фильтре исторических броней: отдельный снимок корпуса при создании брони не хранится.

## Полное совпадение по q

GET /api/rooms?q=A-101 ищет полное название аудитории без учёта регистра. GET /api/admin/bookings?q=... ищет полное имя студента ИЛИ полное название аудитории, без поиска по комментарию. Частичные совпадения не подходят: A-1 не находит A-101. Пробелы по краям q удаляются; отсутствующее, пустое или состоящее из пробелов значение не фильтрует. Внутренние пробелы не изменяются. Символы %, _ и обратный слеш трактуются буквально, не как шаблоны поиска.

Условия выполняются PostgreSQL до получения результатов и объединяются с остальными фильтрами через AND; существующие userId/roomId сохраняются. Если полные имена студентов совпадают, находятся брони всех соответствующих пользователей. Поиск броней использует текущие имена пользователей и названия аудиторий. В /api/rooms фильтр q работает с датой и без неё, в том числе с minDuration. При отсутствии совпадений — 200 с пустым массивом либо пустым rooms в ответе с датой.

Это новое согласование заменяет прежний отказ от q для аудиторий и предложение поиска по подстроке для броней. Сортировка и пагинация административных броней описаны ниже.

## Сортировка и страницы административных броней

GET /api/admin/bookings принимает необязательные sort, limit, offset. sort=date (и отсутствие sort) — дата, начало и ID по возрастанию; sort=-date — те же значения по убыванию; sort=room — название аудитории по алфавиту PostgreSQL, затем дата, начало и ID по возрастанию. Сортировки user нет.

limit — целое от 1 до 100; offset — целое от 0 до 2147483647, по умолчанию 0. Пустые, дробные, отрицательные значения, limit вне диапазона и неизвестный sort дают 400 VALIDATION_ERROR после проверки административного доступа. Без limit возвращаются все совпавшие записи после offset, что сохраняет выгрузку полного списка при отсутствии обоих параметров.

Пример: GET /api/admin/bookings?building=A&sort=-date&limit=20&offset=20. SQL сначала применяет все фильтры (включая точный q), затем сортировку и OFFSET/LIMIT. Ответ остаётся массивом Booking. X-Total-Count — число записей после всех фильтров и до пагинации, включая запросы без limit; на пустой странице счётчик может быть больше 0. Заголовок доступен браузеру через CORS. Для административного списка выполняются два SQL-запроса к броням: COUNT и получение страницы; проверки административного доступа выполняются отдельно. Между этими запросами данные могут измениться из-за параллельной записи. Пагинация не фиксирует снимок на несколько запросов страниц.

Личный список /api/bookings/my не меняется и не выполняет дополнительный COUNT. На ошибках и скрытом административном 404 X-Total-Count не возвращается. X-Active-Count добавлен по правилам раздела счётчиков ниже.

## Предстоящие и прошедшие собственные брони

GET /api/bookings/my?scope=upcoming возвращает только активные брони, у которых дата/время окончания ещё не наступили, включая текущую бронь. scope=past возвращает закончившиеся брони независимо от статуса. Ровно в момент окончания бронь считается прошедшей. Для сравнения один раз берутся текущая локальная дата и время из TimeProvider сервера, с сохранением секунд и долей секунды; фильтрация выполняется в БД.

Без scope прежний список всех собственных броней сохраняется. status и scope объединяются через AND: upcoming&status=cancelled даёт пустой массив, past&status=cancelled — закончившиеся отменённые. Будущие отменённые не входят ни в upcoming, ни в past; их можно получить без scope с status=cancelled. Неизвестный или пустой scope даёт 400 VALIDATION_ERROR. Владелец определяется из JWT, формат массива и сортировка date/startTime/id сохраняются. Автоматической смены статуса нет. Личный список по-прежнему выполняет один запрос к броням, без дополнительного COUNT; проверка существования пользователя отдельная.

## Административная статистика

GET /api/admin/stats?dateFrom=2026-11-15&dateTo=2026-11-21&building=A. Обе даты обязательны, строго YYYY-MM-DD, границы включительные, прошлые даты разрешены. building необязателен, допустимы A/B/C/D. Неверные или пустые параметры и обратный период дают 400 VALIDATION_ERROR после административной проверки. До подтверждения JWT admin и актуальной роли в БД — пустой 404.

Учитываются только active за период, включая уже прошедшие активные брони. Отменённые исключаются. Продолжительность — endTime-startTime в минутах. Ёмкость = все аудитории выбранного корпуса/корпусов × 540 минут × количество календарных дней, включая выходные. Вместимость в людях не участвует. Используются текущие название и корпус аудитории. Данные за прошлые периоды не являются историческим снимком справочника.

Ответ:

- totals: bookings, minutes, percent.
- byBuilding[]: building, rooms, minutes, percent.
- byDay[]: date, bookings, minutes, percent.
- cells[]: building, date, bookings, minutes, capacityMinutes, percent.
- byHalfHour: 18 целых чисел для начал слотов 09:00, 09:30, ... 17:30. Считаются покрытия слота всеми активными бронями периода, конец интервала исключён; одинаковый слот в разных датах суммируется.
- topRooms[]: до 10 аудиторий с бронями, roomId/name/minutes/bookings; по убыванию minutes, затем по name (порядок Ordinal) и roomId.

Процент = minutes × 100 / capacityMinutes, decimal без явного округления; при нулевой ёмкости 0. Без building возвращаются все A-D, включая корпуса без аудиторий; с building — только выбранный. Все даты и клетки возвращаются даже при нулевой занятости. Без броней topRooms пуст, byHalfHour — 18 нулей.

Сервис выполняет три запроса данных: число аудиторий по корпусам; суммы минут и количества по аудитории/дате; количество броней по одинаковым интервалам для получасовых счётчиков. Пользователи, хеши и комментарии не загружаются. Группировки выполняются PostgreSQL, нулевые даты и корпуса добавляются в сервисе. Проверка доступа — отдельный запрос. Общий снимок между запросами не фиксируется; параллельные изменения могут отразиться между вычислениями.

## Счётчики для административного интерфейса

GET /api/rooms (с датой и без неё) и GET /api/rooms/{id} для подтверждённого администратора дополнительно возвращают activeBookings и hasBookings. Для подтверждения нужны роль admin в валидном JWT и актуальная роль admin в БД; применяется существующая политика AdminAccess. При недостаточных правах дополнительные поля отсутствуют, прежний доступ к чтению аудиторий сохраняется. Студент получает прежний набор полей, без null-счётчиков. Ответы POST/PUT и отдельный ответ free-slots не расширяются.

activeBookings — количество active с датой >= сегодняшней локальной даты сервера через TimeProvider, включая уже закончившиеся сегодня. hasBookings — наличие любой брони независимо от даты и статуса; соответствует запрету удаления аудитории с историей. Счётчики относятся ко всей аудитории, не ограничиваются датой/интервалом поиска. Пустая история даёт 0 и false, только отменённые или active до сегодняшней даты — 0 и true. Они вычисляются COUNT/EXISTS в SQL-проекции чтения аудиторий: один запрос данных для списка/карточки, два для списка с доступностью; подтверждение роли выполняется отдельно. Запроса на каждую аудиторию нет. Удаление по-прежнему проверяет FK, поскольку история может появиться после чтения.

GET /api/admin/bookings дополнительно возвращает X-Active-Count: число записей со статусом active после всех переданных фильтров, включая q, и до limit/offset. В отличие от activeBookings аудиторий, самостоятельного ограничения по сегодняшней дате нет: прошлые active тоже считаются. При status=cancelled значение 0; при status=active оно равно X-Total-Count. Оба значения вычисляются одним SQL-агрегатом, затем выполняется запрос страницы (по-прежнему два запроса к броням). На пустой странице счётчики могут быть больше 0; если совпадений нет, оба 0. Заголовок доступен через CORS. На ошибках и скрытом 404 оба счётчика отсутствуют.
