# CampusFlow — frontend

Веб-интерфейс сервиса бронирования аудиторий: найти свободную аудиторию, проверить слот и забронировать — на одном экране.

Стек: React 19 + TypeScript, Vite, React Router, Redux Toolkit + react-redux, Redux-Saga, Axios, SCSS (БЭМ), Vitest.

## Запуск

Для воспроизводимого запуска используйте Node.js 24, как в Docker и CI.

```bash
cd client
npm install
npm run dev
```

Откройте http://localhost:5173. Backend для этого не нужен: по умолчанию включён **mock-режим** — бэкенд работает прямо в браузере, с теми же endpoints, кодами ответов (400/401/403/404/409) и seed-данными, что и в раздаточном материале.

Запуск с реальным backend:

```bash
cp .env.example .env.local   # VITE_USE_MOCK=false, VITE_API_TARGET=http://localhost:8080
npm run dev
```

Dev-сервер проксирует `/api` на `VITE_API_TARGET`, поэтому CORS настраивать не нужно.

Общий запуск фронта, API и PostgreSQL в Docker описан в [корневом README](../README.md#быстрый-запуск-с-нуля-через-docker). Сначала выполняется `init`, затем `up`; текущий внешний адрес — http://localhost:3008. Compose собирает фронт с `VITE_USE_MOCK=false`.

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер на :5173 |
| `npm run build` | проверка типов и production-сборка в `dist/` |
| `npm test` | тесты логики конфликтов, свободных слотов, подбора, CSV, JWT и сценариев приёмки на mock-бэкенде |
| `npm run lint` | oxlint |

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `VITE_USE_MOCK` | `true` | `false` — работать с реальным API |
| `VITE_API_TARGET` | `http://localhost:8080` | куда Vite проксирует `/api` в dev-режиме |
| `VITE_API_BASE` | `/api` | base URL API в браузере |
| `API_UPSTREAM` (Docker) | `http://backend:8080` | куда nginx проксирует `/api` |

## Пользователи (пароль = логин)

| Логин | Имя | Роль |
|---|---|---|
| `student1` | Иван Студентов | student |
| `student2` | Мария Студентова | student |
| `admin` | Администратор Пупкин | admin |

На странице входа есть быстрый вход, а в шапке — переключатель пользователя. Access-токен хранится только в памяти вкладки, вход после перезагрузки восстанавливается через `POST /auth/refresh` по HttpOnly refresh-cookie. В mock-режиме «cookie» эмулируется отдельно для каждой вкладки, поэтому в двух вкладках можно работать под разными пользователями одновременно.

## Что умеет интерфейс

- **Аудитории** (`/`) — фильтры по дате, корпусу, вместимости и оборудованию, необязательный интервал «нужна свободной с … до …». Результаты — схемой кампуса (корпуса × этажи, цвет = занятость на день) или карточками. Справа — шкала дня 09:00–18:00 с шагом 30 минут: интервал выбирается двумя кликами или из списка свободных окон. После брони показывается билет с подтверждением.
- **Подбор** — бонус «рекомендация 3 аудиторий»: число людей, длительность, удобное окно, корпус, оборудование → три варианта с объяснением, почему подошли. Без ML: прозрачная формула (вместимость впритык, раннее окно, корпус, запас времени после).
- **Мои брони** (`/my-bookings`) — предстоящие, прошедшие и отменённые, отмена с подтверждением.
- **Все брони** (`/admin/bookings`, admin) — по умолчанию открываются на сегодня; фильтры по периоду (с — по, быстрые «Сегодня / Завтра / Неделя»), аудитории, пользователю и статусу, отмена любой брони, **экспорт CSV** (открывается в Excel с кириллицей).
- **Справочник** (`/admin/rooms`, admin) — создание, изменение и удаление аудиторий.
- **Аналитика** (`/admin/stats`, admin) — тепловая карта «дни × корпуса», пиковые часы, самые востребованные аудитории.

Администратор не создаёт брони: на главном экране у него только просмотр занятости.

## Демо по сценариям приёмки

1. `student1` → «Завтра», корпус **B**, мест от **20**, **Проектор** → на схеме и в списке остаются B-101 и B-204.
2. Нажмите **B-101** → занято 09:00–10:30, окно 10:30–18:00 свободно.
3. Отметьте на шкале 14:00 и 14:30 → «Забронировать» → билет, бронь в «Моих бронях».
4. Конфликт 409: откройте отдельный профиль браузера под `student2`, выберите тот же интервал в B-101 и, пока он выбран, забронируйте его в первом профиле под `student1`. Нажмите «Забронировать» во втором профиле — придёт `BOOKING_CONFLICT`, конфликтный интервал подсветится красным, шкала обновится.
5. `student1` → «Мои брони» → «Отменить» → статус «Отменена», в расписании слот снова свободен.
6. 403 на чужую бронь: в интерфейсе чужих броней не видно, поэтому в mock-режиме проверка — из консоли браузера под `student2`: `await campusflow.cancelBooking(1)` → `403 FORBIDDEN`. С реальным backend — через Swagger.
7. `admin` → «Все брони» → выбрать завтра или период на три дня → отмена любой брони, например брони `student2`. По умолчанию список открывается на сегодня.

Только в mock-режиме: меню пользователя → «Сбросить демо-данные» возвращает браузерные данные к исходным. С реальным API PostgreSQL так не сбрасывается; seed вызывается явно и сохраняет существующие записи. Порядок подготовки демо — в корневом README.

## API

Base URL `/api`, JSON, даты `YYYY-MM-DD`, время `HH:MM`, заголовок `Authorization: Bearer <token>`. Ошибки — `{code, message, details}`; `message` показывается пользователю, `details` используется для подсветки конфликта.

| Метод | Путь | Где используется |
|---|---|---|
| POST | `/auth/login` | вход |
| POST | `/auth/refresh` | восстановление входа и обновление access по refresh-cookie |
| POST | `/auth/logout` | выход, отзыв refresh-сессии |
| GET | `/rooms?building&minCapacity&equipment=a,b` | справочник, схема кампуса |
| GET | `/rooms/{id}` | — |
| GET | `/rooms/{id}/free-slots?date=` | шкала дня выбранной аудитории |
| GET | `/rooms?date&startTime&endTime&building&minCapacity&equipment` | поиск одним запросом; с `date` ответ `{date, rooms}` |
| POST | `/bookings` | создание брони |
| GET | `/bookings/my?status=` | «Мои брони» |
| DELETE | `/bookings/{id}` | отмена своей брони |
| GET | `/admin/bookings?date&roomId&userId&status` | «Все брони», аналитика. Текущий шлюз отправляет один день как `date`, период фильтрует сам; API уже поддерживает серверные `dateFrom`/`dateTo` |
| DELETE | `/admin/bookings/{id}` | отмена любой брони |
| POST | `/admin/rooms` | создание аудитории |
| PUT | `/admin/rooms/{id}` | изменение аудитории |
| DELETE | `/admin/rooms/{id}` | удаление аудитории; любая связанная бронь → `409 ROOM_HAS_BOOKINGS` |

### Договорённости с backend

Полная сверка — в `FRONTEND_ENDPOINTS.md` в корне репозитория.

- **Поиск одним запросом** — `GET /api/rooms` с `date` (и, при желании, парой `startTime/endTime`); ответ `{date, rooms}`. Путь — константа `SEARCH_PATH` в `src/api/httpGateway.ts`. Запасного обхода нет.
- **Удаление аудитории** — `DELETE /api/admin/rooms/{id}`, `204`. Любая связанная бронь, включая отменённые и прошедшие, даёт `409 ROOM_HAS_BOOKINGS`.
- **Ошибки полей** — `details` вида `{поле: string[]}`; сообщения не по полям формы показываются под формой.
- **Пустой 404** на административных методах — «Операция недоступна», без refresh.
- **Сессия** — access в памяти, один refresh на вкладку (общий Promise), обновление заранее перед истечением, не более одного повтора запроса после refresh; `401` самого refresh — выход с сообщением.
- **Аналитика** считается на клиенте из `GET /admin/bookings` и `GET /rooms`, отдельный API не нужен.
- **Mock ≠ интеграция.** Для проверки с настоящим API запускайте с `VITE_USE_MOCK=false`.

## Структура

```
src/
  api/          axios-клиент, типы, HTTP-шлюз, mock-бэкенд, правила брони, сессия, JWT
  data/         сетка времени, оборудование, подбор, аналитика, CSV
  redux/        store, слайсы (auth, rooms, slots, bookings, admin, ui), саги
  components/   UI по фичам: rooms, slots, bookings, admin, auth, ui, icons
  pages/        страницы-маршруты
  assets/styles/scss/   переменные, base, модули по блокам (БЭМ)
```

Все запросы идут через саги; ошибки API собираются в одном месте (`redux/saga/errors.ts`) и показываются тостами.

## Ограничения MVP

- Mock-режим хранит данные в `localStorage` браузера: у каждого браузера своя «база».
- Шкала свободных слотов не обновляется сама в реальном времени — обновление происходит при смене аудитории или даты и после каждой брони или отмены. Если слот успели занять, backend вернёт 409, и интерфейс это покажет.
- Подбор аудиторий и статистика текущего интерфейса считаются на клиенте. Серверная статистика и дополнительные фильтры уже есть в API, их подключение описано ниже.

## Согласованные расширения API

Полный актуальный контракт и ограничения находятся в [корневом README](../README.md#основной-api) и Swagger. В API реализованы `floor`, `minDuration`, точный `q`, список студентов, период/корпус административных броней, сортировка/пагинация, `scope`, серверная статистика, счётчики и история отмены. Текущий HTTP-шлюз фронта подключает не все эти возможности; наличие API не означает, что каждый параметр уже передаётся из интерфейса.
